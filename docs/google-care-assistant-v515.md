# Google care assistant — v5.15.0

The store owner requested a Google-powered assistant that stays current with newly added products, supports an optional face photo and suggests an affordable personal cosmetic routine. The existing storefront design and product content remain in place. A new owner panel controls activation, model choice, optional images and the daily request cap.

## Product behavior

- The server queries the active, approved, in-stock skincare catalog on every request, including saved Arabic descriptions, benefits, size and use directions. There is no stale copied index, scheduled crawling or model retraining. New products become available after approval and positive stock.
- Candidate discovery uses basic cleanser, moisturizer and sunscreen roles, documented cosmetic preference keywords and affordable alternatives. Retinoids, exfoliants and other active-treatment candidates are excluded from the basic routine. Missing facts are not treated as verified product suitability.
- Google receives a bounded shortlist, the customer's selected preferences, optional consented image and at most six short conversation turns. It returns structured cosmetic guidance and SKU choices.
- The server re-reads live stock and prices after inference, intersects the returned SKUs with its shortlist, removes duplicates and existing cart products, and enforces the specified budget, optionally including shipping. Prices, product links, photos and instructions are resolved by the store, not generated by the model.
- Customer cards link to the normal product pages for reviewing and adding to the existing bag. No order is placed by the assistant.
- Uncertain images produce tentative visible-observation labels only. The assistant is not a diagnostic or treatment service. Concerning reported or visible signs result in a professional referral with no product recommendation. Safety remains limited by model behavior; these safeguards do not establish medical reliability.

## Google setup and privacy

No Google credential or billing account was configured during implementation. Both customer activation and images default to off. The storefront entry remains hidden while unavailable.

The personalized service requires an owner-confirmed Google project with active billing. Google's unpaid-service terms prohibit submission of sensitive, confidential or personal information. Photo and personalized conversation processing cannot be advertised as unrestricted free use. The owner's checkbox does not activate billing or verify billing status; that must be completed directly with Google.

The owner enters an existing API key in the authenticated admin panel. It is encrypted with AES-GCM using a domain-separated HKDF key derived from the existing Worker session secret, never returned by read APIs, and never put in source, public settings or logs. An environment GEMINI_API_KEY can also supply the key. Rotating SESSION_SECRET requires re-entering a database-encrypted key.

Adult confirmation and explicit Google processing consent are required. Photos require an additional per-request consent. The browser converts an uploaded picture into a bounded JPEG from pixel data, discarding original filename and EXIF/GPS metadata. HEIC support depends on the browser decoder; unsupported images receive an actionable JPG/screenshot fallback. The store does not persist images, transcripts, skin profiles or customer identifiers. Only aggregate daily request/image/token/success/failure counts are stored. Google can retain inputs for a limited period under its paid-service terms; the UI does not claim otherwise.

## Operations

- Additive migration: `db/migrations/0030_care_assistant.sql`.
- Owner UI: administration → مساعد العناية.
- Customer UI: `/care-assistant.html`; footer entry shown only after readiness.
- `GET /api/care/status` exposes availability and consent version only.
- `POST /api/care/chat` requires same-origin JSON, the care header, consent, per-IP throttling, owner-enabled paid-project configuration and a global atomic daily reservation.
- `GET/POST /api/admin/care-assistant` uses existing owner-session and write protections, with optimistic revision checks.
- The connection test only checks authenticated model metadata. It does not send customer data, generate an answer, or prove billing/privacy configuration.
- The default cap is 50 requests per UTC day, bounded to 1–500. Failed upstream attempts count. The output cap is 3,072 tokens. These are usage limits, not a guaranteed monetary budget. No automatic retry or paid model switch occurs.
- Supported fixed model IDs are Gemini 3.8 Flash and Gemini 3.5 Flash-Lite, verified against official documentation during development. Upgrades are owner-controlled rather than automatic unreviewed code or model changes.

## Validation and limits

SQLite-backed integration tests cover consent and paid-project gating, fresh catalog additions, mid-inference stock/price changes, unknown SKUs, budget enforcement, cart duplicates, professional referrals, image restrictions, atomic daily limits, upstream failures, encrypted secrets and existing owner authentication. A DOM test covers safe rendering and memory-only conversations.

The complete existing store suite must also pass. Real Google inference and real face interpretation remain unverified until an owner-provided key and paid-project configuration are available. No live test order, customer face or customer transcript is used in validation. Physical iPhone testing is not claimed.

Local release validation on 2026-11-11: all 400 tests passed (including 13 care-assistant tests). The customer form and owner panel were inspected in Chrome using isolated synthetic API responses. A 375 px mobile content viewport had no horizontal overflow; the form uses one column on phones. This validates the interface and store integration safeguards, not Google answer quality or photo accuracy.
